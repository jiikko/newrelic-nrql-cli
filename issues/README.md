# issues/ — issue 管理

運用規約は dotfiles の `issues/README.md` から移植したもの。
dotfiles 固有のツール連携（glogx の issues viewer、`scripts/issue_done.sh`、
`_claude/hooks/*`、`tests/issues/*`）はこのリポジトリには無いため、
**該当箇所は「手で行う」前提に読み替えている**。規約そのものは同じ。

## ファイル命名規約

新規 issue は次の形式で命名する:

```
issues/NNN-<カテゴリ>-<スラッグ>.md
```

- **NNN**: 3 桁ゼロ埋めの連番。**issues/ 配下の全体**（直下・`next/`・`pending/`・`waiting/`・`done/`）で
  最大番号 + 1 を採番する（番号は再利用しない）。状態ディレクトリへ移動してもファイル名は変えないため、
  コードコメント・commit message から「issue 001」で安定して参照できる。
  **`issues/` の外（コード・README）からは必ずこの番号で参照し、`issues/done/001-….md` のような
  裸のパスを書かない**（`done/` へ移すとパスだけが切れる）。パスで書きたいときは markdown リンクにする
- **カテゴリ**: 下表の prefix のいずれか
- **スラッグ**: kebab-case の短い説明。日付を残したい場合は末尾に `-YYYY-MM-DD`

| prefix | 用途 |
|---|---|
| `feat` | 新機能・機能拡張 |
| `bug` | 不具合修正 |
| `refactor` | 挙動を変えない構造改善・複雑性削減 |
| `perf` | 速度・メモリ・リソースの改善（実測の裏付けを本文に置く） |
| `docs` | ドキュメント・コメント整備 |
| `chore` | 雑務（依存更新・CI/ビルド整備・表示の手直しなど、機能でも不具合でもないもの） |
| `research` | 調査・設計検討（成果物がコードでないもの） |
| `human` | **人間しかできない作業**（動作確認・目視レビュー・外部サービスの操作・判断待ち。`期限:` 必須） |
| `retro` | **セッションの振り返り**（実質的な作業をやり切ったら起票。本文の残課題が空になったら done） |

例: `issues/001-feat-verify-against-real-newrelic.md`

次番号の確認（先に `git fetch` して origin 側も数える）:

```sh
git fetch origin
{ find issues -type f -name '[0-9][0-9][0-9]-*.md' | sed 's|.*/||'; \
  git ls-tree -r --name-only origin/main -- issues | sed 's|.*/||'; } |
  grep -E '^[0-9]{3}-' | sort | tail -1
```

## `期限:` — 人が読む期限を本文に書く

本文冒頭のメタ行（`起票日:` の隣）に `期限: YYYY-MM-DD` を書ける。

- **`human` は必須**（人間待ちの作業は放置すると価値が腐るため）。他カテゴリは任意
- **`human` を起票する前に「機械で測れないか」を一度問い、人が要ると判断した理由を本文に書く**
- 書式は**行頭 `期限:` + 半角コロン + `YYYY-MM-DD`**
- 期限は「読んで確認する期限」であって「直す期限」ではない
- **既読の唯一の出典はファイルの位置**（`issues/` にある = 未読、`issues/done/` にある = 確認済み）。
  既読ヘッダー・チェックボックスは使わない（本文を書き換え忘れると嘘が残るため、移動で表す）

## `retro` — セッションの振り返りを流さずに残す

実質的な作業をやり切った時点で `NNN-retro-<スラッグ>-YYYY-MM-DD.md` を起票する。
typo 修正・数行の chore・調査だけで終わったセッションは対象外。

- 中身は「どこで踏んだか / 何が回りくどかったか / 次に効きそうな改善」。うまくいった話は書かない
- **各項目に切り出し先の提案を添える**（新規 issue にする / 却下）。切り出しの実行はユーザーの判断を待つ
- **done の条件は「本文の残課題が空になったこと」**（実装の有無では判定しない）
- 却下した項目は消さずに「却下: 理由」を 1 行残す（同じ気づきが次の retro で再生産されるのを防ぐ）

## ディレクトリ構成

- `issues/*.md` — open な issue
- `issues/next/` — 「次にやる」目印 兼 着手の claim。**中身は issue ファイル本体ではなく
  `NNN-x.md -> ../NNN-x.md` の symlink**（ファイルを動かすと本文の相対リンクが切れるため）
- `issues/pending/` — **凍結**した issue の置き場。着手条件・trigger を本文冒頭に書く。
  再開の主導権は**自分**にある
- `issues/waiting/` — **着手済みだが、こちらから起こせない事象を待っている** issue の置き場。
  pending との違いは**再開の主導権が誰にあるか**（再現待ち・観測待ち・外部イベント待ち）。
  本文冒頭に**待っているもの**と、**それが来たとき何が分かるか**を書く
- `issues/done/` — 完了した issue の移動先（ファイル名は変えずに移動）
- この `README.md` は issue ではない

## 運用ルール

- 対応が完了したら `issues/done/` へ移動する（ファイル名は変えない）。
  移動したら**本文の相対リンクと、他 issue からこの issue への参照を張り直す**
- **issue に関わる作業は、commit のたびに当該 issue の本文へ todolist / 進捗 / 結果 / 残タスクを追記する**
  （chat の報告は流れる。issue 本文が唯一残る）
- issue の記述を鵜呑みにしない。着手前に実コードと git 履歴で検証する（既に修正済み・false positive を弾く）
